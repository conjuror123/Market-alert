# Market Alert

Бот раз в час проверяет курсы выбранных активов — крипта, золото, нефть, индексы,
валюты — и пишет в Telegram, если движение цены выглядит по-настоящему необычно.

Что считать «необычным», алгоритм решает не по жёсткому проценту за день. Он
смотрит, как этот конкретный актив обычно ведёт себя в последнее время, и сравнивает
текущее движение именно с этим.

Работает целиком на GitHub Actions. Ничего дополнительно хостить не нужно.

## Быстрый старт

1. Создайте Telegram-бота через [@BotFather](https://t.me/BotFather) и получите токен.
2. Решите, куда бот будет слать уведомления. Есть два варианта:
   - **Себе лично.** Напишите боту `/start`, затем узнайте свой `chat_id` — например,
     открыв `https://api.telegram.org/bot<TOKEN>/getUpdates` после того как написали
     сообщение.
   - **В канал**, если хотите, чтобы могли подписаться и другие люди. Создайте
     публичный канал и добавьте бота администратором с правом постить сообщения.
     В этом случае `chat_id` — это просто `@username` канала, искать числовой ID
     не нужно.
3. Откройте настройки репозитория: **Settings → Secrets and variables → Actions →
   Secrets**. Добавьте туда `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.
4. Готово — раз в час, в 5 минут после начала часа, бот сам проверит рынок. У
   собственного расписания GitHub Actions есть известная проблема с надёжностью
   (см. блок «Надёжный запуск раз в час» ниже) — рекомендуется дополнительно
   настроить внешний, полностью бесплатный будильник, это буквально 10 минут.

Чтобы убедиться, что всё настроено верно, не дожидаясь реального сигнала: откройте
вкладку **Actions → Test Telegram Notification → Run workflow**. Это отдельная
проверка, она просто присылает тестовое сообщение и ничего больше не делает.

## Какие активы отслеживаются

По умолчанию — десять: Bitcoin, Ethereum, Solana, золото, нефть WTI, S&P 500,
30-летние облигации США, EUR/USD, USD/CNY и индекс доллара (DXY).

Список активов — в файле `config/config.yaml`. Чтобы добавить или убрать актив,
достаточно отредактировать этот файл — код менять не нужно.

<details>
<summary><b>Как добавить новый актив</b></summary>

1. Найдите тикер и проверьте его вживую, а не по памяти — не все тикеры, которые
   кажутся логичными, реально существуют. Например, для индекса доллара `DX=F`
   не сработал (404, такого тикера нет), а `DX-Y.NYB` — сработал. Быстрая проверка:
   ```bash
   python3 -c "
   from price_monitor import yahoo   # или price_monitor.coinbase
   import requests
   candles = yahoo.fetch_klines('ТИКЕР', '1h', limit=20,
       base_url='https://query1.finance.yahoo.com', session=requests.Session())
   print(len(candles), candles[-1].close, candles[-1].volume)
   "
   ```
2. Добавьте запись в `assets:` в `config/config.yaml` — `symbol`, `source`,
   `label`, и `news_query`, если `label` не годится как поисковый запрос.
3. Прогоните бэктест и посмотрите на новый актив в отчёте:
   ```bash
   python -m price_monitor.backtest --days 365 --out data/backtest_results.json
   ```
   Смотрите на три вещи: частоту уведомлений в неделю, recall на топ-5 крупнейших
   движений, и не выглядят ли числа структурно сломанными (как было у S&P 500 с
   объёмом или у USD/CNY с залипшими котировками — см. блок про бэктест выше).
4. Если что-то структурно не так с этим конкретным активом — добавьте точечный
   override прямо в его запись в `config.yaml` (см. «Индивидуальные пороги по
   активу» ниже), а не подкручивайте общие пороги под один актив.
5. Учтите: у общих порогов сейчас есть целевая суммарная частота по всем активам
   вместе (см. блок про бэктест выше) — добавление актива эту сумму слегка поднимет
   на его собственный вклад. Разово это не страшно, но если активов накопится
   много, имеет смысл прогнать бэктест по всем сразу и, возможно, пересчитать общие
   пороги — это на ваше усмотрение.

</details>

## Как бот решает, что писать

У каждого актива своя обычная волатильность: то, что для облигаций — землетрясение,
для криптовалюты — рядовой день. Поэтому вместо фиксированного процента алгоритм
сравнивает последнее движение цены с тем, насколько сильно этот актив обычно
колеблется прямо сейчас. Если спокойный актив вдруг резко дёрнулся — это тревога.
Если актив и так постоянно скачет на такую величину — это не тревога, а рутина.

Между уведомлениями по одному активу выдерживается пауза (по умолчанию 14 дней),
чтобы не заваливать чат повторами по одному и тому же событию. Но если за это время
случится что-то по-настоящему крупное и новое, уведомление всё равно придёт — пауза
не заставит вас пропустить действительно важное.

Если хочется получать уведомления чаще или реже, для этого есть один параметр —
`price_zscore_threshold` в `config/config.yaml`. Чем меньше его значение, тем чаще
будут срабатывать алерты; чем больше — тем реже.

Есть ещё одна, необязательная возможность: по запросу попросить LLM объяснить уже
отправленный алерт по свежим новостям и дописать причину прямо в то же сообщение в
Telegram. Она не часть обычного часового цикла — запускается вручную и требует
отдельной настройки, подробности в блоке «Объяснение алерта через LLM и новости»
ниже.

Как всё это устроено внутри — в блоках ниже. Читать их для повседневного
использования не обязательно: они для тех, кому интересны детали или кто хочет
тонко всё настроить.

<details>
<summary><b>Как именно считается «аномалия»</b></summary>

Вместо простого процента за день используются два независимых сигнала:

1. **EWMA-волатильность** — адаптивная оценка того, насколько сильно актив
   колеблется прямо сейчас. Быстро подстраивается под смену режима: если рынок
   несколько дней штормит, «нормальным» временно считается более широкий размах.
2. **Робастный z-score по медиане/MAD** на скользящем окне — более консервативная,
   долгоиграющая оценка нормы. В отличие от обычного стандартного отклонения, её
   не «раздувает» один прошлый скачок. Свечи без изменения цены (залипшая
   котировка — типичная ситуация в тихие часы на форексе) в это окно намеренно не
   попадают: иначе рядовое движение начинает выглядеть как экстремальный выброс.

По умолчанию алерт по цене срабатывает, только если **оба** сигнала одновременно
превышают порог `price_zscore_threshold`. Это отсекает случайные срабатывания
одного метода. Но у такого подтверждения есть слабое место: если значение только
**одного** сигнала экстремально само по себе, второй может по инерции остаться чуть
ниже порога — и событие пропадёт впустую. Поэтому есть отдельный, более высокий
порог, `price_zscore_override`: если его пересекает хотя бы один сигнал,
подтверждение второго уже не требуется. Объём проверяется тем же способом — обычно
нужно подтверждение умеренным движением цены (`volume_zscore_threshold`), а при
экстремальном значении объёма (`volume_zscore_override`) — не нужно.

Пауза между уведомлениями тоже устроена не как жёсткий таймер. Повторный алерт во
время паузы всё равно отправится в двух случаях: если он в `escalation_factor` раз
крупнее того, что вызвало предыдущий алерт, или если он экстремален сам по себе
(пересекает `price_zscore_override`/`volume_zscore_override`) — тогда пауза
игнорируется полностью. Логика этой части — в `price_monitor/state.py`. Состояние
по каждому активу хранится в `data/state.json` и коммитится обратно в репозиторий
после каждого запуска.

</details>

<details>
<summary><b>Проверено бэктестом на реальных исторических данных</b></summary>

Скрипт `price_monitor/backtest.py` прогоняет ровно ту же логику, что используется в
проде, по каждому часу реальной истории за выбранный период. Он не просто проверяет,
сработал бы сигнал — он симулирует, дошло бы уведомление на самом деле, с учётом
паузы между алертами.

```bash
python -m price_monitor.backtest --days 365 --out data/backtest_results.json
```

Вот что получилось при прогоне на 10 активах за примерно год с текущими порогами:

| Актив | Уведомлений в неделю | Recall |
|---|---|---|
| Bitcoin | 0.19 | 2/5 |
| Ethereum | 0.29 | 4/5 |
| Solana | 0.25 | 3/5 |
| Золото | 0.27 | 3/5 |
| Нефть WTI | 0.34 | 4/5 |
| S&P 500 | 0.22 | 2/5 |
| 30Y Treasury | 0.25 | 3/5 |
| EUR/USD | 0.15 | 4/5 |
| USD/CNY | 0.22 | 2/5 |
| Индекс доллара (DXY) | 0.21 | 4/5 |

Суммарно по всем 10 активам — около **2.4 уведомления в неделю**: это и есть
осознанная цель, а не побочный эффект. Более ранняя версия порогов (на 9 активах,
до добавления DXY) была настроена на противоположную задачу — не пропустить вообще
ничего крупного — и в реальном использовании оказалась слишком шумной, около 22
уведомлений в неделю суммарно. Текущие пороги пересчитаны бэктестом заново под
другую цель: 0-1 уведомление в неделю суммарно в спокойное время, 2-3 — в самые
турбулентные периоды. Добавление актива поднимает эту суммарную цифру — баланс
между числом активов и частотой уведомлений на весь набор в целом решать вам.

Recall здесь — это доля из 5 крупнейших часовых движений каждого актива за год,
которые бот реально бы поймал; итог — **31 из 50**. При настройке на редкие
уведомления recall неизбежно ниже, чем при настройке на максимальный охват — это
прямое следствие выбранной цели, а не недосмотр. Большая часть «пропусков» —
не потерянный сигнал, а намеренная работа паузы между уведомлениями: несколько
крупных движений подряд в рамках одного турбулентного эпизода (например, обвал длится
не один час, а несколько) схлопываются в одно уведомление вместо серии, и бэктест
засчитывает как «пропуск» те из них, что не стали первым уведомлением об эпизоде.

По пути к этому результату бэктест нашёл и помог исправить несколько реальных
проблем:

- Простая пауза без исключений теряла события, которые случаются кучно — например,
  несколько крупных скачков подряд во время одного обвала. Решение — параметр
  `escalation_factor`, о котором рассказано выше: пропускает по-настоящему
  усиливающуюся ситуацию сквозь паузу, а не только первое событие в серии.
- Часть пограничных случаев не проходила дуальное подтверждение вообще, ни при каком
  размере паузы. Для этого добавлены пороги `price_zscore_override` и
  `volume_zscore_override`.
- У USD/CNY источник данных (Yahoo) часто присылал «залипшую» свечу без обновления
  цены, из-за чего обычные движения ошибочно выглядели как выбросы. Это исправлено
  в самом `analysis.py` — такие свечи исключены из расчёта, а не замаскировано
  подкручиванием порога.
- У S&P 500 объём торгов оказался структурно непригоден для такого расчёта: из-за
  суточной сезонности NYSE z-score по объёму мог доходить почти до 100. Канал по
  объёму для этого актива просто отключён, работает только сигнал по цене.

Полная версия отчёта с графиками — на
[дашборде бэктеста](https://claude.ai/code/artifact/de0b0c0f-533d-447f-a18a-35f18bf4ee14).
Это приватная ссылка, доступная вам; если захотите поделиться ею с кем-то ещё, это
можно сделать через меню Share на странице.

</details>

<details>
<summary><b>Особенности источников данных</b></summary>

| source     | что покрывает                          | формат symbol                    | пример          |
|------------|-----------------------------------------|-----------------------------------|-----------------|
| `coinbase` | крипто-споты (Coinbase Exchange)        | `BASE-QUOTE`                      | `BTC-USD`       |
| `yahoo`    | фьючерсы, индексы, форекс (Yahoo Finance)| тикер как на finance.yahoo.com    | `GC=F`, `EURUSD=X` |

- **У форекс-пар нет объёма.** Для спот-валютных пар (`EURUSD=X`, `CNY=X`) единого
  биржевого объёма не существует, и Yahoo всегда присылает `volume=0`. Для таких
  активов работает только ценовой сигнал — это ожидаемое поведение, а не баг.
- **Фьючерсы иногда «прыгают» на смене контракта.** Тикеры вида
  `GC=F`/`CL=F`/`ES=F`/`ZB=F` — это «непрерывный» контракт ближайшего месяца. При
  экспирации Yahoo сам переключает его на следующий, и в этот момент возможен
  ценовой гэп, никак не связанный с реальным движением рынка. Такое случается пару
  раз в год на актив.
- **API Yahoo Finance неофициальный.** Используется недокументированный
  chart-эндпоинт — официального бесплатного API для фьючерсов, индексов и форекса
  не существует. Он стабильно работает уже много лет, но Yahoo может ограничить его
  без предупреждения. Если активы с `source: yahoo` вдруг начнут постоянно падать,
  проверять стоит в первую очередь это.
- **Binance не используется.** Изначально рассматривался как источник крипто-данных,
  но его публичный API отдаёт HTTP 451 (гео-блокировку) с IP-адресов США — а именно
  там обычно находятся стандартные раннеры GitHub Actions.

</details>

<details>
<summary><b>Индивидуальные пороги по активу</b></summary>

Любой параметр можно переопределить для конкретного актива прямо в
`config/config.yaml` — достаточно добавить нужный ключ в его запись. Например, так
для S&P 500 отключён канал по объёму:

```yaml
assets:
  - symbol: "ES=F"
    source: yahoo
    label: "S&P 500 (E-mini futures)"
    volume_zscore_threshold: 200.0   # фактически отключает канал объёма
    volume_zscore_override: 200.0
```

Переопределить можно любой из этих ключей: `interval`, `lookback`, `mad_window`,
`ewma_lambda`, `price_zscore_threshold`, `price_zscore_override`,
`volume_zscore_threshold`, `volume_zscore_override`, `volume_min_price_move_z`,
`cooldown_minutes`, `escalation_factor`, `min_history`. Всё, что не переопределено
для конкретного актива, берётся из общих настроек в том же файле.

Пороги настраиваются на трёх уровнях, от общего к частному:

1. Значение по умолчанию в коде.
2. Значение из `config.yaml`, если оно там задано.
3. Переменная окружения (те же имена, но в верхнем регистре, плюс
   `HEALTH_ALERT_AFTER_FAILURES` и `HEALTH_REMINDER_EVERY_FAILURES`).
4. Override у конкретного актива в `config.yaml`.

Каждый следующий уровень перекрывает предыдущий.

</details>

<details>
<summary><b>Алерт на отказ самого мониторинга</b></summary>

Если получение данных или отправка в Telegram не удаются несколько запусков подряд
(по умолчанию три, настраивается параметром `health_alert_after_failures`),
приходит отдельное сообщение «мониторинг не работает» со списком причин. Пока
проблема не устранена, время от времени приходит напоминание — по умолчанию раз в
сутки (`health_reminder_every_failures`), а не при каждом запуске. Когда всё снова
заработает, придёт сообщение «мониторинг восстановился».

Есть один случай, который это не покроет: если сам `TELEGRAM_BOT_TOKEN` или
`TELEGRAM_CHAT_ID` неверны, или бот заблокирован, сообщить об этом через тот же
Telegram, разумеется, не получится. Тогда единственным сигналом будет красный ❌
у workflow во вкладке Actions.

</details>

<details>
<summary><b>Объяснение алерта через LLM и новости</b></summary>

Каждый отправленный алерт всегда сохраняется в `data/alerts_log.json` — вместе с
номером сообщения в Telegram, чтобы его потом можно было отредактировать. Это
происходит само по себе и ни от чего не зависит. А вот дописать в алерт вероятную
причину («почему актив упал/вырос») можно только по запросу, отдельным шагом:

1. Заведите API-ключ у любого провайдера с OpenAI-совместимым API (по умолчанию
   настроен [DeepSeek](https://platform.deepseek.com/) — недорого и без лишних
   формальностей). Пополните там баланс — оплата по токенам, без ключа шаг работать
   не будет.
2. Добавьте ключ в **Settings → Secrets and variables → Actions → Secrets**, под
   любым именем — например, `DEEPSEEK_API_KEY`.
3. В файле `.github/workflows/explain-alerts.yml` укажите, какой секрет
   использовать, в строке `LLM_API_KEY: ${{ secrets.ВАШЕ_ИМЯ_СЕКРЕТА }}`.
4. Запускайте, когда нужно объяснить конкретный алерт: вкладка **Actions →
   Explain Alerts → Run workflow**. Поле **Message ID** обязательное — этот номер
   написан мелким текстом в конце самого сообщения в Telegram (строка вида
   `ID: 12345`), скопируйте его туда. Поле сделано обязательным намеренно: без
   него один запуск случайно потратил бы токены сразу на всю накопившуюся очередь
   необъяснённых алертов, а не на один конкретный.

При запуске бот берёт указанный алерт, ищет заголовки новостей по активу через
Google News (ключ не нужен) и отправляет их вместе с цифрами алерта в LLM с
просьбой связать новость с движением цены в 2-3 предложениях на русском. Если
подходящей новости не нашлось, модели явно велено так и написать, а не придумывать
причину. Готовое объяснение дописывается в конец исходного сообщения в Telegram
через редактирование поста — новое уведомление не создаётся.

Новости ищутся строго в окне **с 6 по 12 час после алерта** — это фиксированный
отрезок времени относительно самого алерта, а не «от алерта до сейчас». Из
соображений экономии смысла нет: заголовок стоит ничтожно мало по токенам, поэтому
всё, что попало в окно, целиком уходит в LLM без дополнительной обрезки. Такое окно
было выбрано, чтобы почти всегда захватывать разумное количество непосредственно
относящихся к делу новостей, не размывая его ни совсем свежими предположениями (в
первые часы после события обычно есть только сам факт, без анализа причин), ни
случайными более поздними событиями не по теме. Соответственно, шаг вообще не
возьмётся за алерт, пока с момента отправки не пройдёт `explain_min_age_hours` часов
(по умолчанию 12, совпадает с концом окна) — иначе окно оказалось бы обработано не
целиком. Более младшие алерты остаются в очереди до следующего запуска.

Раньше окно не имело верхней границы («от алерта до сейчас»), и правильная граница
зависела от того, когда именно нажали «Run workflow» — измени я запрос на минуту
позже, получил бы другой набор новостей. С фиксированным окном результат
детерминирован: сколько раз ни запускай explain для одного и того же алерта, окно
поиска (и, значит, набор новостей) не меняется.

Границы окна передаются в Google двумя его собственными операторами поиска —
`after:` и `before:`. Проверено вживую (на летней и на зимней дате, то есть через
переход на летнее/зимнее время): Google считает сутки не по UTC, а по времени
Тихоокеанского побережья США (America/Los Angeles) — видимо, из-за параметров
запроса `hl=en-US`/`gl=US`. Даты для `after:`/`before:` пересчитываются в этот пояс
через `zoneinfo` перед тем, как попасть в запрос, а не берутся с суточным запасом
на глаз — так удаётся не потерять новости на границе суток и при этом не запрашивать
у Google лишние дни.

Это не автоматика, а инструмент по запросу: стоит какое-то (небольшое, по-токенное)
количество денег и требует API-ключ, поэтому не встроено в обычный часовой цикл
мониторинга.

Чтобы сменить LLM-провайдера позже, менять код не нужно: `price_monitor/llm.py`
умеет говорить с любым сервисом, у которого есть эндпоинт `/chat/completions` в
формате OpenAI (так устроены DeepSeek, OpenAI, OpenRouter и большинство остальных).
Меняются только `llm_base_url`, `llm_model_peak`/`llm_model_offpeak` в
`config/config.yaml`, плюс то, какой секрет подставлен в `LLM_API_KEY` на шаге 3
выше.

По умолчанию используются две разные модели DeepSeek в зависимости от времени
суток — так дешевле. У DeepSeek в «пиковые» часы (01:00–04:00 и 06:00–10:00 UTC по
будням — это 04:00–07:00 и 09:00–13:00 по летнему времени Израиля (IDT, UTC+3) или
03:00–06:00 и 08:00–12:00 по зимнему (IST, UTC+2)) цена полная, а всё остальное
время — вдвое дешевле. Поэтому в пик берётся более простая и дешёвая модель
(`deepseek-v4-flash`), а в остальное время — более сильная (`deepseek-v4-pro`),
которая за счёт скидки обходится сопоставимо. Это же расписание продублировано в
описании поля Message ID в самой форме "Run workflow" (на английском часовом поясе
UTC плюс израильском), чтобы не пересчитывать в уме перед запуском. Если у вашего
провайдера нет деления на пиковые часы, просто укажите одну и ту же модель в обеих
настройках.

Для каждого актива, у которого удобное для поиска название не совпадает с `label`
(например, «Золото (Gold futures)»), в `config/config.yaml` есть необязательное
поле `news_query` — обычный текстовый запрос для поиска новостей.

<details>
<summary><b>Надёжный запуск раз в час</b></summary>

Собственное расписание GitHub Actions (`schedule:` в yml-файле) — штука ненадёжная
на малоактивных репозиториях: вместо заявленного «раз в час» GitHub Actions
реально может запускать job раз в 5-10 часов. Это задокументированное поведение
самого GitHub («best effort», а не гарантия), а не баг в этом проекте — поэтому
в `price-monitor.yml` расписания больше нет, только `workflow_dispatch`, и запуск
раз в час обеспечивает внешний бесплатный сервис.

1. Заведите **fine-grained personal access token** на github.com →
   Settings → Developer settings → Personal access tokens → Fine-grained tokens.
   Repository access → только этот репозиторий. Permissions → **Actions: Read and
   write** — больше ничего отмечать не нужно. Поставьте срок действия (fine-grained
   токены не бывают бессрочными — раз в год придётся перевыпустить).
2. Зарегистрируйтесь на [cron-job.org](https://cron-job.org/) (бесплатно, без
   карты) и создайте задание:
   - URL: `https://api.github.com/repos/ВАШ_АККАУНТ/ВАШ_РЕПОЗИТОРИЙ/actions/workflows/price-monitor.yml/dispatches`
   - Метод: **POST**
   - Заголовки: `Authorization: Bearer ВАШ_ТОКЕН` и `Accept: application/vnd.github+json`
   - Тело запроса: `{"ref": "ИМЯ_ВЕТКИ"}` (ветка, на которой лежит workflow)
   - Расписание: каждый час.

Токен даёт право только запускать workflow в этом одном репозитории — прочитать
код, секреты или что-либо ещё им нельзя.

## Локальный запуск

```bash
pip install -r requirements-dev.txt
export TELEGRAM_BOT_TOKEN=...
export TELEGRAM_CHAT_ID=...
python -m price_monitor
```

Тесты запускаются командой `pytest -q`.

## Ограничения

- Оба источника данных не отдают больше ~300 свечей за один запрос. Если понадобится
  увеличить `lookback` сверх 300, придётся либо уменьшить `mad_window`/`interval`,
  либо добавить пагинацию в `coinbase.py`/`yahoo.py`.
- У `price-monitor.yml` больше нет собственного расписания — без настройки
  внешнего будильника (см. «Надёжный запуск раз в час» выше) мониторинг не
  запустится сам вообще, только вручную через Run workflow.
