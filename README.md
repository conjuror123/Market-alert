# Market Alert — умный монитор ценовых аномалий

Приложение раз в час (через GitHub Actions) забирает свежие свечи с публичных API,
оценивает, насколько последнее движение цены и объёма выбивается из **обычного для
этого конкретного актива** поведения за последнее время, и шлёт уведомление в
Telegram, если это действительно похоже на аномалию, а не на рутинный шум.

По умолчанию отслеживаются: **Bitcoin, Ethereum, Solana** (крипта, Coinbase
Exchange), **золото, нефть WTI, S&P 500, 30-летние облигации США** (фьючерсы, Yahoo
Finance) и **EUR/USD, USD/CNY** (форекс, Yahoo Finance) — см. `config/config.yaml`.

Статистика считается на **часовых свечах**: у Coinbase лимит 300 свечей за запрос, и
на часовках это ≈12.5 дней истории (вместо ≈3.1 дня, если бы брались 15-минутки) —
база для z-score получается заметно надёжнее. Опрос API синхронизирован с этим же
таймфреймом и идёт раз в час.

## Почему не «просто % за день»

Фиксированный процент (например, «алерт, если цена изменилась на 5% за день») не
учитывает, что у разных активов разная базовая волатильность, и что волатильность
одного и того же актива меняется во времени. Вместо этого используются два
согласованных сигнала:

1. **EWMA-волатильность** (RiskMetrics, λ по умолчанию 0.94) — адаптивная оценка
   «нормального» размаха движения для актива прямо сейчас. Быстро подстраивается под
   смену режима волатильности.
2. **Робастный z-score по медиане/MAD** на скользящем окне — устойчивая к прошлым
   выбросам базовая линия (обычное стандартное отклонение легко «раздувается» одним
   предыдущим скачком, медиана/MAD — нет).

Алерт по цене срабатывает, только если **оба** сигнала одновременно превышают порог
— это отсекает случайные срабатывания одного метода.

Дополнительно считается робастный z-score объёма: если объём аномально вырос **и**
при этом было хотя бы умеренное движение цены, это тоже триггерит уведомление
(всплеск объёма часто предшествует или сопровождает резкое движение). Для валютных
пар (спот-форекс) единого биржевого объёма не существует, поэтому по ним работает
только ценовой сигнал — см. «Активы и источники данных» ниже.

Чтобы не заспамить чат повторными алертами по одному активу, между уведомлениями по
одному активу выдерживается cooldown (по умолчанию 2 часа) — состояние хранится в
`data/state.json` и коммитится обратно в репозиторий workflow'ом после каждого запуска.

## Алерт на отказ самого мониторинга

Если получение данных или отправка в Telegram упали хотя бы по одному активу
несколько запусков подряд (`health_alert_after_failures`, по умолчанию 3 — то есть
~3 часа при часовом опросе), приходит отдельное сообщение «мониторинг не работает» с
перечнем того, что именно сломалось. Пока проблема не устранена, раз в
`health_reminder_every_failures` неудачных запусков (по умолчанию 24, то есть
примерно раз в сутки) приходит напоминание, чтобы долгую проблему не забыть, но не
спамить каждый час. Когда всё снова начинает работать — приходит сообщение
«мониторинг восстановился». Логика — в `price_monitor/health.py`, состояние (счётчик
подряд идущих неудачных запусков) хранится в том же `data/state.json`.

Есть один неустранимый случай: если сам `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`
неверны или бот заблокирован, отправить уведомление об этом, разумеется, тоже не
получится — в этом случае единственный сигнал будет красный ❌ у workflow во вкладке
Actions репозитория, стоит иногда туда заглядывать.

## Бэктест порогов

`price_monitor/backtest.py` прогоняет ровно ту же логику, что и прод (`analyze()` из
`price_monitor/analysis.py`, формулы не продублированы), по каждому часу реальной
истории за выбранный период — walk-forward, без заглядывания вперёд: на шаге `i`
видны только данные до `i`. Собирает по каждому активу: частоту алертов при текущих
порогах, сколько сработало бы при одном сигнале (только EWMA / только робастный)
против обоих сразу, сравнение с наивным фиксированным % порогом, и чувствительность
частоты алертов к `price_zscore_threshold`.

```bash
python -m price_monitor.backtest --days 365 --out data/backtest_results.json
```

Данные — те же публичные источники, что и в проде: Coinbase постранично докачивается
за пределы обычного 300-свечного лимита (`coinbase.fetch_full_history`), Yahoo отдаёт
до ~2 лет часовых баров одним запросом. Результат сохраняется в JSON и печатается
сводкой в терминал.

Прогон на реальных 9 активах за ~год показал:

- **Требование «оба сигнала согласны» реально работает**: в среднем ~66% (57–88% по
  активам) срабатываний, которые дал бы один робастный z-score сам по себе, отсеиваются,
  когда EWMA не подтверждает движение.
- **Recall 96%** на 5 крупнейших часовых движениях каждого актива за год (43 из 45
  пойманы при текущих порогах) — алгоритм не пропускает по-настоящему большие события.
- **Найден реальный дефект и исправлен per-asset overrid'ом**: у форекс-пар (особенно
  USD/CNY, 18% часовых свечей — «залипшая» котировка без обновления) MAD-база на
  почти нулевой истории схлопывается, и обычное движение получает завышенный z-score
  (пример из бэктеста: движение всего на 0.37% дало robust z-score −173.75). Для
  `CNY=X` в `config.yaml` поднят `price_zscore_threshold` до 4.0 — компенсирующая
  мера, подтверждённая повторным прогоном бэктеста: **4.8/нед → 2.6/нед**, теперь
  сопоставимо с EUR/USD (2.7/нед). Настоящий фикс — не учитывать в MAD свечи без
  изменения цены — пока не сделан, это отдельное изменение `analysis.py`.
- **Подтверждён на живом примере риск ролловера фьючерсов** из раздела «Активы и
  источники данных»: три из пяти крупнейших часовых движений WTI за год оказались
  скачком и почти полным откатом в течение суток 8–9 марта — это гэп на смене
  контракта у Yahoo, а не рыночное событие. Здесь фикса нет — детекция отработала
  верно, дело в качестве данных, а не в порогах; такие алерты по фьючерсам стоит
  перепроверять руками, если дата совпадает с известной датой экспирации контракта.
- **S&P 500 futures шумил по объёму сильнее остальных и тоже исправлен**: у биржевых
  фьючерсов объём предсказуемо подскакивает на открытии сессии почти каждый торговый
  день, и общий `volume_min_price_move_z=1.5` этого не отсеивал — 864 из 897 алертов
  за год были по объёму, ~22/неделю. Для `ES=F` подняты `volume_zscore_threshold` до
  5.0 и `volume_min_price_move_z` до 3.0 — повторный прогон подтвердил:
  **21.9/нед → 9.3/нед**, актив перестал быть выбросом на фоне остальных.

Все три находки и цифры до/после — в наглядном виде на
[дашборде бэктеста](https://claude.ai/code/artifact/de0b0c0f-533d-447f-a18a-35f18bf4ee14)
(приватная ссылка, доступна вам; поделиться можно через меню Share на странице).

## Активы и источники данных

Каждый актив в `config/config.yaml` — это `symbol` (тикер) + `source` (откуда брать
данные) + `label` (как называть актив в уведомлении):

| source     | что покрывает                          | формат symbol                    | пример          |
|------------|-----------------------------------------|-----------------------------------|-----------------|
| `coinbase` | крипто-споты (Coinbase Exchange)        | `BASE-QUOTE`                      | `BTC-USD`       |
| `yahoo`    | фьючерсы, индексы, форекс (Yahoo Finance)| тикер как на finance.yahoo.com    | `GC=F`, `EURUSD=X` |

Дефолтный набор активов и их Yahoo-тикеры:

| Актив                         | symbol      |
|--------------------------------|-------------|
| Золото                         | `GC=F`      |
| Нефть WTI                      | `CL=F`      |
| S&P 500 (E-mini фьючерс)       | `ES=F`      |
| 30-летние облигации США        | `ZB=F`      |
| EUR/USD                        | `EURUSD=X`  |
| USD/CNY                        | `CNY=X`     |

Чтобы добавить/убрать актив — правьте список `assets` в `config/config.yaml`, код
менять не нужно. Полный список доступных Yahoo-тикеров можно найти поиском на
[finance.yahoo.com](https://finance.yahoo.com) (символ инструмента показан там же,
на странице котировки).

### Индивидуальные пороги по активу

Бэктест по 9 активам наглядно показал: один и тот же порог не подходит всем — у
биржевых фьючерсов своя суточная сезонность объёма, у некоторых валютных пар свои
особенности качества котировок, у крипты своя базовая волатильность. Рассчитан
проект максимум на ~сотню активов, так что индивидуальная настройка каждого себя
окупает — это не агрессивная оптимизация под общий знаменатель.

Любой из этих параметров можно переопределить прямо в записи актива в
`config/config.yaml`: `interval`, `lookback`, `mad_window`, `ewma_lambda`,
`price_zscore_threshold`, `volume_zscore_threshold`, `volume_min_price_move_z`,
`cooldown_minutes`, `min_history`. Всё, что не переопределено — берётся из общих
настроек ниже по файлу. Пример (уже применённый, по итогам бэктеста):

```yaml
assets:
  - symbol: "ES=F"
    source: yahoo
    label: "S&P 500 (E-mini futures)"
    volume_min_price_move_z: 3.0   # было 1.5 — общий порог фильтровал слишком мягко
    volume_zscore_threshold: 5.0   # было 4.0

  - symbol: "CNY=X"
    source: yahoo
    label: "USD/CNY"
    price_zscore_threshold: 4.0    # было 3.0 — компенсация залипших котировок
```

Разрешение параметров и логика — `Config.params_for()` в `price_monitor/config.py`;
и прод (`__main__.py`), и бэктест (`backtest.py`) используют один и тот же resolver,
так что цифры в отчёте бэктеста всегда отражают то, что реально включено для
каждого актива.

Особенности источников, которые стоит знать:

- **Форекс без объёма.** У спот-валютных пар (`EURUSD=X`, `CNY=X`) Yahoo всегда
  отдаёт `volume=0` — единого биржевого объёма для форекса не существует. Для таких
  активов работает только ценовой сигнал (EWMA + робастный z-score); сигнал по
  объёму для них не сработает никогда, и это ожидаемо, а не баг.
- **Ролловер фьючерсов.** Тикеры вида `GC=F`/`CL=F`/`ES=F`/`ZB=F` — это
  «непрерывный» контракт ближайшего месяца: при экспирации Yahoo сам переключает
  его на следующий контракт, и в этот момент возможен ценовой гэп, не связанный с
  реальным движением рынка. Такое бывает всего несколько раз в год на актив и может
  изредка вызвать ложный алерт.
- **Yahoo Finance API неофициальный.** Официального бесплатного API для
  фьючерсов/индексов/форекса не существует — используется недокументированный
  chart-эндпоинт Yahoo. Он много лет стабильно работает у множества open-source
  проектов, но Yahoo может изменить или ограничить его без предупреждения; если
  workflow начнёт постоянно падать на активах с `source: yahoo`, это первое, что
  стоит проверить.
- **Binance не используется.** Изначально рассматривался как источник крипто-данных,
  но его публичный API отдаёт HTTP 451 (гео-блокировка) с IP-адресов США — а именно
  там обычно находятся стандартные раннеры GitHub Actions.

## Структура

```
price_monitor/
  config.py      — загрузка config/config.yaml + переопределение через env/secrets
  coinbase.py    — публичный REST-клиент Coinbase Exchange (крипто), ключ не нужен
  yahoo.py       — публичный chart-клиент Yahoo Finance (фьючерсы/индексы/форекс)
  market_data.py — выбирает нужный клиент по полю source у актива
  models.py      — общие типы (Candle, ExchangeError)
  analysis.py    — EWMA-волатильность, робастный z-score, логика алертов
  notifier.py    — отправка сообщений в Telegram
  state.py       — cooldown между ценовыми алертами
  health.py      — алерт на отказ самого мониторинга (см. раздел ниже)
  __main__.py    — точка входа одного прогона мониторинга
config/config.yaml — список активов и пороги
data/state.json     — персистентное состояние (коммитится обратно в репо)
.github/workflows/
  price-monitor.yml — запуск раз в час (cron) + workflow_dispatch
  tests.yml          — юнит-тесты на push/PR
tests/                — pytest-тесты для analysis.py, config.py, yahoo.py, state.py, health.py
```

## Настройка

1. Создайте Telegram-бота через [@BotFather](https://t.me/BotFather), получите
   `TELEGRAM_BOT_TOKEN`. Узнайте `TELEGRAM_CHAT_ID` (например, через
   `https://api.telegram.org/bot<TOKEN>/getUpdates` после того как напишете боту).
2. В настройках репозитория **Settings → Secrets and variables → Actions → Secrets**
   добавьте:
   - `TELEGRAM_BOT_TOKEN`
   - `TELEGRAM_CHAT_ID`
3. Список активов задаётся в `config/config.yaml` (раздел `assets`) — правьте его
   напрямую и коммитьте, отдельной secret/variable для этого нет.
4. Убедитесь, что workflow `price-monitor.yml` находится на **дефолтной ветке**
   репозитория — GitHub Actions запускает `schedule`-триггеры только с дефолтной
   ветки. После смёржа PR в основную ветку планировщик заработает автоматически на
   ближайшем часовом тике (5-я минута каждого часа); расписания cron в GitHub Actions
   могут срабатывать с задержкой в периоды высокой нагрузки на инфраструктуру GitHub.
5. Права `contents: write` уже прописаны в workflow — они нужны, чтобы job мог
   закоммитить обновлённый `data/state.json` обратно в репозиторий.

## Локальный запуск

```bash
pip install -r requirements-dev.txt
export TELEGRAM_BOT_TOKEN=...
export TELEGRAM_CHAT_ID=...
python -m price_monitor
```

Тесты:

```bash
pytest -q
```

## Настройка порогов

Список активов меняется только в `config/config.yaml`. Пороги настраиваются на трёх
уровнях, от общего к частному: жёсткое значение по умолчанию в коде → значение из
`config.yaml` → переменная окружения (`INTERVAL`, `LOOKBACK`, `MAD_WINDOW`,
`EWMA_LAMBDA`, `PRICE_ZSCORE_THRESHOLD`, `VOLUME_ZSCORE_THRESHOLD`,
`VOLUME_MIN_PRICE_MOVE_Z`, `COOLDOWN_MINUTES`, `MIN_HISTORY`,
`HEALTH_ALERT_AFTER_FAILURES`, `HEALTH_REMINDER_EVERY_FAILURES`) → override у
конкретного актива в `config.yaml` (см. «Индивидуальные пороги по активу» выше) —
самый частный уровень всегда побеждает.

## Ограничения

- Оба источника отдают не более ~300 свечей за один запрос на используемом
  таймфрейме — при увеличении `lookback` свыше 300 либо уменьшайте
  `mad_window`/`interval`, либо добавляйте пагинацию в `coinbase.py`/`yahoo.py`.
- `interval` можно переопределить и по отдельному активу, но Yahoo не поддерживает
  нативную 6-часовую свечу (в отличие от Coinbase) — для активов с `source: yahoo`
  используйте `1m`/`5m`/`15m`/`1h`/`1d`.
- GitHub Actions cron не гарантирует запуск точно в 5-ю минуту каждого часа — в
  моменты высокой нагрузки на инфраструктуру GitHub старты могут задерживаться на
  несколько минут.
