# Market Alert

Бот, который раз в час проверяет курсы выбранных активов (крипта, золото, нефть,
индексы, валюты) и пишет в Telegram, если движение цены выглядит по-настоящему
необычно — не по жёсткому проценту, а с оглядкой на то, как этот актив обычно
ведёт себя в последнее время.

Работает целиком на GitHub Actions — ничего хостить не нужно.

## Быстрый старт

1. Создайте Telegram-бота через [@BotFather](https://t.me/BotFather), получите токен.
2. Решите, куда слать уведомления:
   - **Себе лично** — напишите боту `/start`, узнайте свой `chat_id` (например
     через `https://api.telegram.org/bot<TOKEN>/getUpdates` после сообщения).
   - **В канал**, чтобы могли подписаться и другие — создайте публичный канал,
     добавьте бота администратором с правом постить сообщения. Тогда `chat_id` —
     это просто `@username` канала, числовой ID искать не нужно.
3. В репозитории: **Settings → Secrets and variables → Actions → Secrets**,
   добавьте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.
4. Готово. Раз в час (в :05) бот сам проверит рынок. Убедиться, что всё настроено
   верно, не дожидаясь реального сигнала: **Actions → Test Telegram Notification
   → Run workflow** — придёт тестовое сообщение.

## Какие активы отслеживаются

По умолчанию — 9 штук: Bitcoin, Ethereum, Solana, золото, нефть WTI, S&P 500,
30-летние облигации США, EUR/USD, USD/CNY.

Список — в `config/config.yaml`, добавить или убрать актив можно прямо там, без
правки кода.

## Как бот решает, что писать

Вместо фиксированного процента алгоритм сравнивает последнее движение цены с тем,
насколько сильно этот актив обычно колеблется прямо сейчас. Спокойный актив, который
вдруг резко дёрнулся, — тревога; актив, который и так постоянно скачет на этот
процент, — нет.

Чтобы не заваливать чат повторами по одному и тому же событию, между уведомлениями
по активу есть пауза (по умолчанию 14 дней) — но по-настоящему крупное новое событие
всё равно дойдёт, не дожидаясь её конца.

Хотите уведомлений больше или меньше — крутите один параметр
`price_zscore_threshold` в `config/config.yaml` (меньше значение — чаще алерты,
больше — реже). Как это устроено внутри — в раскрывающихся блоках ниже, для
понимания настройки читать не обязательно.

<details>
<summary><b>Как именно считается «аномалия»</b></summary>

Используются два независимых сигнала вместо простого % за день:

1. **EWMA-волатильность** — адаптивная оценка «нормального» размаха движения для
   актива прямо сейчас, быстро подстраивается под смену режима волатильности.
2. **Робастный z-score по медиане/MAD** на скользящем окне — устойчивая к прошлым
   выбросам базовая линия (обычное стандартное отклонение легко «раздувается» одним
   предыдущим скачком, медиана/MAD — нет). Свечи без изменения цены (залипшая
   котировка — типично для тихих часов на форексе) в это окно не попадают, иначе
   рядовое движение начинает выглядеть как экстремальный выброс.

Алерт по цене срабатывает, если **оба** сигнала одновременно превышают
`price_zscore_threshold` — отсекает случайные срабатывания одного метода. Но если
значение **одного** сигнала экстремально само по себе (порог
`price_zscore_override`), подтверждение второго не требуется — так не пропускаются
события, для которых обычное подтверждение слишком строгое. Объём считается так же:
обычный порог `volume_zscore_threshold` требует ещё и умеренного движения цены, а
`volume_zscore_override` — нет.

Повторный алерт во время паузы (`cooldown_minutes`) всё равно уходит, если он в
`escalation_factor` раз крупнее того, что вызвало предыдущий, либо — независимо от
паузы вообще — если он экстремален сам по себе (пересекает
`price_zscore_override`/`volume_zscore_override`). Логика — в
`price_monitor/state.py`, состояние по каждому активу — в `data/state.json`
(коммитится обратно в репозиторий после каждого запуска).

</details>

<details>
<summary><b>Проверено бэктестом на реальных исторических данных</b></summary>

`price_monitor/backtest.py` прогоняет ровно ту же логику, что и прод, по каждому
часу реальной истории за выбранный период — включая симуляцию того, ушло бы
уведомление реально (с учётом паузы), а не просто «сигнал сработал».

```bash
python -m price_monitor.backtest --days 365 --out data/backtest_results.json
```

Итог на 9 активах за ~год, с текущими порогами:

| Актив | Увед./неделю | Recall |
|---|---|---|
| Bitcoin | 3.89 | 5/5 |
| Ethereum | 2.80 | 5/5 |
| Solana | 2.09 | 5/5 |
| Золото | 2.29 | 5/5 |
| Нефть WTI | 1.86 | 5/5 |
| S&P 500 | 2.93 | 5/5 |
| 30Y Treasury | 2.89 | 5/5 |
| EUR/USD | 0.83 | 5/5 |
| USD/CNY | 2.02 | 5/5 |

**Recall 45/45** — ни одно из 5 крупнейших часовых движений ни одного из 9 активов
за год не потеряно. 8 из 9 активов держатся в 0–3 уведомлениях в неделю; Bitcoin
чуть выше (3.89) — крипта объективно даёт больше независимых крупных движений в год,
чем остальные классы активов, дальше снижать нечем (не зажаты паузой).

По пути бэктест нашёл и поправил несколько реальных проблем:
наивная пауза без исключений теряла кластеризованные во времени события (recall
падал до 35/45, отсюда `escalation_factor`); часть пограничных случаев дуальное
подтверждение не пропускало вообще (отсюда `*_override`); у USD/CNY Yahoo часто
отдаёт «залипшую» свечу без обновления цены, что искусственно занижало базовую
линию — исправлено в `analysis.py` (такие свечи исключены из расчёта), а не
подкручиванием порога; у S&P 500 объём оказался структурно непригоден для z-score
(суточная сезонность NYSE даёт z-score под 100) — канал объёма для него отключён.

Полная версия с графиками — на
[дашборде бэктеста](https://claude.ai/code/artifact/de0b0c0f-533d-447f-a18a-35f18bf4ee14)
(приватная ссылка, доступна вам; поделиться можно через меню Share на странице).

</details>

<details>
<summary><b>Особенности источников данных</b></summary>

| source     | что покрывает                          | формат symbol                    | пример          |
|------------|-----------------------------------------|-----------------------------------|-----------------|
| `coinbase` | крипто-споты (Coinbase Exchange)        | `BASE-QUOTE`                      | `BTC-USD`       |
| `yahoo`    | фьючерсы, индексы, форекс (Yahoo Finance)| тикер как на finance.yahoo.com    | `GC=F`, `EURUSD=X` |

- **Форекс без объёма.** У спот-валютных пар (`EURUSD=X`, `CNY=X`) единого
  биржевого объёма не существует — Yahoo всегда отдаёт `volume=0`, для таких активов
  работает только ценовой сигнал, и это ожидаемо, а не баг.
- **Ролловер фьючерсов.** Тикеры вида `GC=F`/`CL=F`/`ES=F`/`ZB=F` — «непрерывный»
  контракт ближайшего месяца: при экспирации Yahoo сам переключает его на следующий
  контракт, и в этот момент возможен ценовой гэп, не связанный с реальным движением
  рынка. Бывает пару раз в год на актив.
- **Yahoo Finance API неофициальный** — используется недокументированный
  chart-эндпоинт, официального бесплатного API для этих классов активов не
  существует. Стабильно работает годами, но Yahoo может ограничить его без
  предупреждения; если `source: yahoo` начнёт постоянно падать, это первое, что
  стоит проверить.
- **Binance не используется** — его публичный API отдаёт HTTP 451 (гео-блокировка)
  с IP-адресов США, а именно там обычно находятся раннеры GitHub Actions.

</details>

<details>
<summary><b>Индивидуальные пороги по активу</b></summary>

Любой параметр можно переопределить для конкретного актива прямо в
`config/config.yaml` — просто добавьте нужный ключ в его запись:

```yaml
assets:
  - symbol: "ES=F"
    source: yahoo
    label: "S&P 500 (E-mini futures)"
    volume_zscore_threshold: 200.0   # фактически отключает канал объёма
    volume_zscore_override: 200.0
```

Переопределяемые ключи: `interval`, `lookback`, `mad_window`, `ewma_lambda`,
`price_zscore_threshold`, `price_zscore_override`, `volume_zscore_threshold`,
`volume_zscore_override`, `volume_min_price_move_z`, `cooldown_minutes`,
`escalation_factor`, `min_history`. Всё, что не переопределено — берётся из общих
настроек в том же файле.

Пороги настраиваются на трёх уровнях, от общего к частному: значение по умолчанию в
коде → `config.yaml` → переменная окружения (те же имена в верхнем регистре, плюс
`HEALTH_ALERT_AFTER_FAILURES`, `HEALTH_REMINDER_EVERY_FAILURES`) → override у
конкретного актива — самый частный уровень побеждает.

</details>

<details>
<summary><b>Алерт на отказ самого мониторинга</b></summary>

Если получение данных или отправка в Telegram упали несколько запусков подряд
(`health_alert_after_failures`, по умолчанию 3), приходит отдельное сообщение
«мониторинг не работает» со списком причин. Пока не починится — редкое напоминание
(`health_reminder_every_failures`, по умолчанию раз в сутки), а не спам каждый час.
Когда всё снова заработало — придёт «мониторинг восстановился».

Один случай это не покроет: если сам `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` неверны
или бот заблокирован — сообщить об этом через тот же Telegram, разумеется, не
получится. Тогда единственный сигнал — красный ❌ у workflow во вкладке Actions.

</details>

data/state.json     — персистентное состояние (коммитится обратно в репо)
.github/workflows/

  test-notify.yml    — ручной запуск test_notify.py из вкладки Actions

tests/                — pytest-тесты на все модули выше

## Локальный запуск

```bash
pip install -r requirements-dev.txt
export TELEGRAM_BOT_TOKEN=...
export TELEGRAM_CHAT_ID=...
python -m price_monitor
```

Тесты: `pytest -q`

## Ограничения

- Источники данных не дают больше ~300 свечей за один запрос — при увеличении
  `lookback` свыше 300 либо уменьшайте `mad_window`/`interval`, либо добавляйте
  пагинацию в `coinbase.py`/`yahoo.py`.
- GitHub Actions cron не гарантирует запуск точно в 5-ю минуту каждого часа — в
  моменты высокой нагрузки на инфраструктуру GitHub старты могут задерживаться.
